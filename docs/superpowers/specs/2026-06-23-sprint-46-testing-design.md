# Sprint 46 - 测试补齐设计文档

## 1. 背景

当前项目已经具备较完整的截图、编辑、OCR、AI、长截图与设置页能力，
但测试环节仍主要分散在各个 Sprint 文档的“人工验证”描述中：

- 缺少正式的 `XCTest` 自动测试 target
- 缺少统一的自动测试运行说明
- 缺少单独整理、可重复执行的人工测试清单

这会导致后续多人协作时，
很难快速判断哪些核心逻辑有自动回归保护，
也不利于每个 Sprint 收尾时形成稳定、一致的验证流程。

Sprint 46 的目标不是一次性把整个项目做成高覆盖率测试工程，
而是先补齐一套真实可运行、可维护、可扩展的最小测试体系。

---

## 2. 目标

本次 Sprint 需要完成：

- 新增项目正式的 `XCTest` 单元测试 target
- 为当前稳定、纯逻辑、无系统权限依赖的模块补第一批自动测试
- 新增自动测试文档，说明如何运行、覆盖范围与扩展原则
- 在当前 Sprint 文档中补齐人工测试附录，形成可执行清单
- 将测试补齐纳入 `ROADMAP` 与当前 Sprint 文档，作为正式开发环节的一部分

本次 Sprint 完成后，项目应具备：

- 一条可本地执行的自动测试命令
- 一组稳定、不依赖 UI 和系统授权环境的单元测试
- 一份针对真实主链路的人工测试 checklist
- 一套后续 Sprint 可继续沿用的测试文档结构

---

## 3. 不做的内容

本次 Sprint 明确不做：

- 不引入 `XCUITest` / UI 自动化测试
- 不为所有业务 service 一次性补全测试
- 不为了测试重构大块现有业务结构
- 不引入新的第三方测试框架（如 Quick / Nimble）
- 不改变当前 AppKit + SnapKit 的 UI 技术方向

原因很简单：
当前仓库还没有测试基座，
第一版应优先建立“能稳定跑起来”的自动测试闭环，
而不是直接进入高成本、易脆弱的 UI 自动化阶段。

---

## 4. 方案对比

### 方案 A：只补测试文档，不补工程内自动测试

优点：

- 实现快
- 改动小

缺点：

- 不能形成真实的自动回归能力
- 不满足“补上测试环节”的核心目标

### 方案 B：补 `XCTest` 单元测试基座 + 自动测试文档 + 当前 Sprint 人工测试附录

优点：

- 改动范围可控
- 可以立即形成可执行自动测试
- 与当前项目“逻辑层先测、UI 先人工回归”的现实状态匹配
- 便于后续逐步扩展测试覆盖

缺点：

- 第一版覆盖范围有限
- 暂时不能自动验证 UI 交互

### 方案 C：单元测试 + UI 自动化一起上

优点：

- 理论覆盖更完整

缺点：

- 当前工程尚无稳定 UI 自动化基础
- 会显著增加实现复杂度和维护成本
- 第一版很容易引入脆弱测试

本次 Sprint 采用方案 B。

---

## 5. 自动测试范围设计

### 5.1 选取原则

第一批自动测试只覆盖以下类型的代码：

- 纯逻辑
- 配置解析
- 枚举映射
- 不依赖窗口、权限、截图设备、系统事件监听
- 输入输出明确，断言稳定

这样可以最大程度降低测试脆弱性，
并快速让测试成为“日常可跑”的开发动作。

### 5.2 第一批测试对象

建议优先覆盖：

- `ScreenshotHotKey`
  - 存储值序列化
  - 旧格式兼容解析
  - 非法存储值拒绝
  - 候选快捷键过滤
  - 显示名称拼接
- `KeyEquivalentNameMap`
  - 已支持键码映射正确
  - 不支持键码返回 `nil`
- `AppLanguage`
  - `system` 语言解析到实际语言
  - 多种 `preferredLanguages` 输入映射正确
  - OCR 识别语言顺序符合预期
- `AppLocalization`
  - 用户设置读取逻辑正确
  - 未设置时回退默认值
  - 非法值回退到 `system`
- `AppSettings`
  - 默认值常量与约定键名存在回归保护

如果实现过程中发现 `AppAppearance`、`RGBColor` 等对象几乎零成本即可补测，
可一并纳入；但不应为了追求数量拉大范围。

### 5.3 测试边界

本轮不直接测试以下内容：

- `ScreenCaptureKit` 截图链路
- `Vision` OCR 真机识别结果
- AI 网络请求
- 菜单栏交互
- 设置页 AppKit 控件交互
- Overlay / 标注画布行为
- 长截图窗口与预览窗口 UI

这些能力暂时仍以人工测试为主。

## 6. 工程结构设计

新增一个标准 `XCTest` 单元测试 target，
命名与路径保持直接、清晰：

- `TYScreenShotToolTests/`
  - `Hotkey/ScreenshotHotKeyTests.swift`
  - `Hotkey/KeyEquivalentNameMapTests.swift`
  - `Shared/AppLanguageTests.swift`
  - `Shared/AppLocalizationTests.swift`
  - `Shared/AppSettingsTests.swift`

必要时新增一个测试辅助文件，例如：

- `TYScreenShotToolTests/TestSupport/TestUserDefaults.swift`

用于创建隔离的 `UserDefaults` suite，
避免测试污染本机真实配置。

原则：

- 测试文件按被测模块归类
- 每个测试文件只负责一个明确对象
- 尽量不新增生产代码层抽象
- 若需要可测试性调整，只做最小改动

## 8. 人工测试设计

人工测试附录按真实用户链路组织，
每条都需要写明“步骤”和“预期结果”，
避免只有标题、没有执行标准。

建议覆盖以下分组：

1. 启动与菜单栏
2. 全局截图热键
3. 普通截图编辑态
4. 设置页
5. OCR / AI 结果链路
6. 长截图主链路
7. 复制 / 保存 / Pin 等输出能力

人工测试目标不是穷尽所有像素级场景，
而是确保当前版本最重要的真实用户流程有明确回归手册。

---

## 9. 错误处理与可维护性策略

为避免测试体系刚建立就变得难维护，
本轮采用以下策略：

- 自动测试只碰稳定逻辑，不追求覆盖率数字
- 测试使用隔离的 `UserDefaults`，避免污染本地环境
- 测试断言尽量直接针对输入输出，不依赖复杂初始化
- 测试命名以“行为”表达，不以实现细节命名
- 文档明确哪些能力仍需人工验证，避免误导为“已有全自动保障”

如果某个对象为了测试需要大面积拆分或重构，
应视为超出本轮范围，优先缩小测试目标而不是扩大改造面。

---

## 10. 验证方案

本次 Sprint 的验证分为两部分：

### 10.1 自动验证

- 成功创建并接入 `XCTest` test target
- 测试可以通过统一命令稳定运行
- 第一批单元测试全部通过

### 10.2 人工验证

- 按 `Sprint 46` 附录逐项执行主链路检查
- 确认测试补齐过程未影响现有截图、设置、OCR、AI、长截图功能

最终交付标准：

- 工程内有正式自动测试 target
- 自动测试文档可指导他人独立执行
- 当前 Sprint 文档中有可执行人工测试附录
- 构建与测试命令均有真实验证记录

---

## 11. 结果预期

Sprint 46 完成后，
项目会从“主要依赖人工口头验证”前进一步，
进入“自动测试 + 人工测试并存”的状态：

- 自动测试负责保护稳定逻辑和配置解析
- 人工测试负责覆盖高价值用户链路和 UI 行为

这不是最终形态，
但它会成为后续每个 Feature / Sprint 都能继续复用的测试起点。
