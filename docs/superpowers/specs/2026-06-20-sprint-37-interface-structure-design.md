# Sprint 37 - 界面结构识别设计文档

## 1. 背景

Sprint 35 已完成 `AI` 菜单与 `摘要总结`，
Sprint 36 又完成了 `翻译语言`，
现在普通截图与长截图中的 `AI` 入口已经支持：

- `开发报错分析`
- `摘要总结`
- `翻译语言`

同时，
两条截图链路已经继续复用 Sprint 34 的双输入能力：

- `本地 OCR -> AI 文本分析`
- `AI 视觉取字 -> AI 文本分析`

此前已经明确，
后续希望继续把 `AI` 菜单扩展为多方向入口，
其中一个高频方向就是：

- UI / 代码识别

但本轮不直接进入“生成 HTML/CSS / SwiftUI / Figma 组件名映射”。

Sprint 37 的目标先收敛为：

1. 在当前 `AI` 菜单中新增一级项 `界面结构识别`
2. 让普通截图与长截图都支持这一能力
3. 输出一份“设计 + 开发混合”的单段结构化描述，
   供设计师、开发者或后续 AI 继续复用

---

## 2. 本轮目标

Sprint 37 要完成的内容：

- 在当前 `AI` 菜单中新增一级菜单项：
  - `界面结构识别`
- 普通截图与长截图都支持相同入口
- 保持当前 Settings 中双输入链路不变
- 结果继续复用当前 `AI` 结果窗容器
- 本轮结果窗只展示一段结构化文本
- 结构化文本同时覆盖设计信息与实现提示

---

## 3. 用户故事

### 用户故事 1

作为截图用户，
我希望选中一个网页或 App 界面元素后，
可以直接让 AI 识别它的结构与语义，
这样我不需要自己再手动拆解截图里的界面层次。

### 用户故事 2

作为设计师或开发者，
我希望 AI 给我的不是泛泛而谈的描述，
而是一份可继续复用的结构化说明，
这样我可以把它继续交给设计、前端、原生开发或其他 AI。

### 用户故事 3

作为普通截图与长截图混合使用的用户，
我希望 `界面结构识别` 的入口与行为保持一致，
这样我的 `AI` 使用心智不会因为截图模式不同而变化。

---

## 4. 范围

### Included

- 在普通截图 `AI` 菜单中新增一级项 `界面结构识别`
- 在长截图 `AI` 菜单中新增一级项 `界面结构识别`
- 继续复用 Sprint 34 的双输入链路：
  - 本地 OCR
  - AI 视觉取字
- 输出单段结构化文本结果
- 结构化文本覆盖：
  - 组件识别
  - 结构层级
  - 视觉特征
  - 交互语义
  - 实现提示
- `实现提示` 采用混合风格：
  - 先给通用实现描述
  - 再补一句前端 / 原生都可参考的实现方向
- 继续复用当前 `AI` 结果窗
- 支持 `复制全部`
- 支持 `复制结构`
- 继续保留普通截图与长截图现有重试语义
- 继续保留长截图现有结果窗摆放规则与异步失效保护

### Out of Scope

- 直接生成 `HTML/CSS`
- 直接生成 `SwiftUI` / `AppKit` 代码
- 输出 Figma 组件名或自动映射设计系统
- 区分 Web / App 两套菜单入口
- 区分 Web / App 两套结果窗
- 新增设置页开关
- 表格数据提取
- 文本翻译、摘要、待办提取混入该能力
- 独立 `UI` 分析窗口
- JSON 风格结果输出

## 5. 设计方案

### 5.1 菜单交互

本轮继续复用 Sprint 35 已建立的 `AI` 菜单交互。

点击 `AI` 按钮后：

- 普通截图：
  在底部工具栏 `AI` 按钮上方弹出菜单
- 长截图：
  在底部操作区 `AI` 按钮上方弹出同样菜单

Sprint 37 后的一级菜单项调整为：

1. `开发报错分析`
2. `摘要总结`
3. `翻译语言 >`
4. `界面结构识别`

本轮不为 `界面结构识别` 增加二级子菜单。

原因是：

- 这轮只做一个最小能力方向
- 先降低菜单复杂度
- 以后如果这一方向继续扩展出“结构识别 / 代码生成 / 组件命名”等子能力，
  再考虑拆成分组

---

### 5.2 普通截图与长截图一致性

本轮要求普通截图与长截图中的 `界面结构识别` 体验保持一致：

1. 点 `AI`
2. 选择 `界面结构识别`
3. 开始分析
4. 展示结构化描述结果

这样可以保证：

- 用户不需要区分普通截图与长截图的 `AI` 心智
- 后续若继续扩展同方向能力，
  两条截图链路也不需要维护两套入口

---

### 5.3 双输入链路保持不变

Sprint 37 不重做 Sprint 34 已完成的取字链路。

仍然按当前 Settings 开关决定输入方式：

- 开关关闭：
  `截图 -> 本地 OCR -> AI 界面结构识别`
- 开关打开：
  `截图 -> AI 视觉取字 -> AI 界面结构识别`

Sprint 37 的变化只在“AI 要做什么”这一层：

- `开发报错分析`
- `摘要总结`
- `翻译语言`
- `界面结构识别`

也就是说，
菜单负责决定“AI 的分析方向”，
Settings 开关继续负责决定“AI 输入从哪里来”。

---

### 5.4 结果结构

Sprint 37 不新增第二种 `AI` 结果窗。

继续复用当前 `AI` 结果窗容器，
但 `界面结构识别` 的内容区只展示一段结构化文本。

这段文本内部保持固定小标题顺序：

1. `组件识别`
2. `结构层级`
3. `视觉特征`
4. `交互语义`
5. `实现提示`

其中：

- `组件识别`
  说明截图中的界面更像什么元素
- `结构层级`
  说明大致由哪些层组成，谁包着谁
- `视觉特征`
  说明布局、对齐、主次、颜色感受、圆角、边框、间距等
- `交互语义`
  说明它更像静态展示、可点击入口、状态切换项还是信息容器
- `实现提示`
  先给通用实现方向，再补一句前端 / 原生都可参考的落地建议

本轮不把这 5 段拆成 5 个独立 section view，
而是统一放进一段结构化文本中。

这样设计的原因是：

- 更适合直接复制给设计 / 开发 / 其他 AI
- 更符合当前用户选择的“单段结构化文本”方向
- 可避免过早把结果窗做成新的多段模式

---

### 5.5 输出内容边界

本轮 `界面结构识别` 只做“结构化描述”。

AI 输出必须聚焦：

- 这是一个什么界面元素
- 这个元素大致由什么层组成
- 视觉上有什么显著特征
- 它承担什么交互语义
- 如果继续做设计或开发，推荐如何理解和落地

本轮不承诺：

- 精确像素级还原
- 精确设计系统命名
- 直接生成代码
- 自动判断某个商业设计系统中的真实组件名

这样可以把范围严格收敛到 MVP，
先交付“可用描述”，
而不是一次背上“识别 + 建模 + 生代码”全链路。

---

### 5.6 复制语义

`界面结构识别` 结果窗底部按钮继续复用当前统一结构：

- `复制全部`
- `复制结构`
- `重试`
- `关闭`

其中：

- `复制全部`
  - 复制当前结果窗完整结构化文本
- `复制结构`
  - 复制同一份结构化文本
  - 与 `复制全部` 在本轮语义几乎一致，
    但保留单独命名，
    方便后续如果增加额外说明时继续区分

复制成功后：

- 只关闭 `AI` 结果窗
- 不退出普通截图编辑态
- 不退出长截图模式

这与 Sprint 35、Sprint 36 收口后的复制行为保持一致。

---

### 5.7 状态文案

选择 `界面结构识别` 后：

- loading 文案：
  `AI 正在识别界面结构...`
- 结果状态：
  `界面结构识别`
- 二级复制按钮：
  `复制结构`
- 复制成功 toast：
  `界面结构已复制`

这样可以与：

- `开发报错分析`
- `摘要总结`
- `翻译语言`

保持同一套 mode 驱动文案体系。

---

### 5.8 错误与重试语义

本轮继续复用当前用户已经熟悉的错误语义：

- 如果截图里没有足够有效内容：
  - 只提示 `AI 未识别到有效内容`
  - 不保留结果窗
- 如果 AI 请求失败：
  - 提示 `AI 分析失败`
  - 支持重试
- 点击 `重试` 后：
  - 保持当前方向仍然是 `界面结构识别`
  - 不重新弹菜单

长截图模式中继续保留：

- 当前结果窗左右摆放规则
- 请求过期保护

这样可以最大程度复用 Sprint 32、35、36 已建立的交互心智。

## 6. 技术方案选择

### 方案 A：继续复用 `AIAnalysisService`，新增 `界面结构识别` mode

做法：

- 在现有 `AIAnalysisMode` 上新增一个一级能力：
  - `interfaceStructure`
- 菜单层只多一个一级菜单项
- `CaptureSessionService` 继续按当前 mode 编排普通截图与长截图流程
- `AIAnalysisService` 增加一套 prompt 与解析规则
- `AI` 结果窗继续复用当前容器

优点：

- 改动最小
- 与 Sprint 35 / 36 的扩展路径完全一致
- 普通截图 / 长截图 / 重试 / 摆放 / 复制语义都能最大程度复用
- 最符合 MVP

缺点：

- `AIAnalysisService` 继续承载更多 AI 文本输出职责
- 后续能力继续变多时仍需评估是否拆分

---

### 方案 B：新增独立 `AIInterfaceStructureService`

做法：

- 单独新建一个 service
- 它自己负责 prompt、请求与结果解析
- `CaptureSessionService` 按 mode 分流到不同 service

优点：

- 职责更清晰
- 为后续做“结构识别 / 组件命名 / 代码生成”留出更清楚的边界

缺点：

- 对本轮来说偏早
- 需要额外增加 service 分流与接口层
- 超出当前 MVP 复杂度

---

### 方案 C：直接用视觉模型看图分析，不复用当前双输入链路

做法：

- 不再依赖当前 OCR / 视觉取字得到的文本输入
- 直接把截图交给视觉模型做结构识别

优点：

- 理论上更适合纯图形界面识别
- 对文字较少、图形较多的界面可能更准确

缺点：

- 会偏离 Sprint 34 已稳定的输入链路
- 会把本轮变成“重新定义 AI 输入策略”的大迭代
- 风险与范围都明显超出本轮目标

---

### 本轮推荐方案

Sprint 37 推荐采用：

- 方案 A：继续复用 `AIAnalysisService`

推荐原因：

1. 和当前 `AI` 菜单演进路径最一致
2. 普通截图与长截图的现有收口能力都能最大程度复用
3. 能最快交付“结构化描述”这条最小价值链路
4. 如果后续继续做代码生成或 Web / App 分流，
   可以等这一轮稳定后再拆 service

---

## 7. 验收标准

1. 普通截图点击 `AI` 后，可看到一级菜单项 `界面结构识别`
2. 长截图点击 `AI` 后，也可看到一级菜单项 `界面结构识别`
3. 选择 `界面结构识别` 后，结果窗继续复用当前 `AI` 结果窗容器
4. 结果窗只展示一段结构化文本，而不是新的多段窗口
5. 结构化文本中固定包含：
   - `组件识别`
   - `结构层级`
   - `视觉特征`
   - `交互语义`
   - `实现提示`
6. `复制全部` 与 `复制结构` 都只关闭结果窗，不退出当前模式
7. `AI 使用视觉取字` 开关关闭时，能力继续走本地 OCR 链路
8. `AI 使用视觉取字` 开关打开时，能力继续走视觉取字链路
9. 无有效内容时，只提示 `AI 未识别到有效内容`
10. 失败时提示 `AI 分析失败` 并支持重试
11. 重试时保持原分析方向，不重新弹菜单
12. 长截图中的结果窗继续遵守当前左右摆放规则与异步过期保护

---

## 8. 非目标

Sprint 37 明确不做：

- 生成 HTML / CSS
- 生成 SwiftUI / AppKit 代码
- Figma 组件映射
- Web / App 分平台 prompt 分流
- JSON 结构化结果
- 设置页新增开关
- 新窗口类型
- 批量界面识别
- 多区域界面对比分析

---

## 9. 结论

Sprint 37 的定位是：

在当前 `AI` 菜单体系上，
新增一个最小可用的一级能力：

- `界面结构识别`

它不直接生成代码，
也不提前做复杂平台分流，
而是先交付一份可被设计、开发和后续 AI 继续利用的结构化描述。

这样既符合当前项目的 MVP / KISS / YAGNI 原则，
也为后续更强的 `UI / 代码识别` 能力留出了稳定入口。
