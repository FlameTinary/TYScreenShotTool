# Sprint 34 - AI 视觉取字分析设计文档

## 目标

在现有截图编辑体验中，
为 `AI` 分析增加一个可切换的新输入链路：

- 开关关闭时，继续使用当前老链路  
  `截图 -> 本地 OCR -> AI 文本分析 -> AI 结果窗`
- 开关打开时，使用新链路  
  `截图 -> AI 视觉取字 -> AI 文本分析 -> AI 结果窗`

本轮目标不是替换现有 `OCR` 功能，
而是在保持当前稳定链路可用的前提下，
让 `AI` 分析具备“直接看图取字再分析”的能力。

同时本轮也为后续更通用的 `AI` 能力扩展预留基础，
例如：

- 摘要总结
- 翻译语言
- 待办提取
- 表格转 CSV
- UI / 代码识别

这些方向本轮只记录为后续需求，
不进入当前实现范围。

---

## 背景

当前项目已经具备：

- 截图编辑态
- `OCR` 按钮与 `OCR` 结果预览窗口
- `AI` 按钮与 `AI` 结果窗口
- 长截图 `AI` 分析

当前 `AI` 分析实际依赖的是：

`截图 -> 本地 OCR -> AI 文本分析`

这条链路的问题不是不能工作，
而是产品语义上用户点击的是 `AI`，
但底层依赖的其实仍是系统 OCR。

因此本轮需要补上一条真正的“AI 看图取字”路径，
但又不能直接丢掉当前稳定的老链路。

最合适的做法是：

1. 在 `Settings` 中增加一个开关
2. 默认关闭，保持当前行为不变
3. 打开后，让 `AI` 改走视觉模型取字
4. `OCR` 按钮与 `OCR` 结果窗口保持原样

---

## 目标用户

核心用户：

- 单人开发者
- 使用截图工具分析 `Xcode` 报错、终端输出、日志文本的用户

本轮间接受益用户：

- 想比较“本地 OCR”与“AI 视觉取字”效果差异的用户

本轮不直接面向：

- 通用图像理解工作流
- 表格提取与导出
- 设计稿转代码
- UI 组件识别

## 需求

### 功能需求

1. 在 `Settings` 页面中增加一个新的 AI 开关。
2. 开关文案为：
   - 标题：`AI 使用视觉取字`
   - 说明：`关闭时使用本地 OCR，开启时使用 AI 先识别截图文字再分析。`
3. 开关默认值为关闭。
4. 开关关闭时，普通截图与长截图中的 `AI` 都继续走当前老链路：
   - `截图 -> 本地 OCR -> AI 文本分析 -> AI 结果窗`
5. 开关打开时，普通截图与长截图中的 `AI` 都改走新链路：
   - `截图 -> AI 视觉取字 -> AI 文本分析 -> AI 结果窗`
6. `OCR` 按钮与 `OCR` 结果预览窗口保持原样，不受此开关影响。
7. 普通截图与长截图的 `AI` 结果窗口继续复用当前结构：
   - `报错大意`
   - `可能原因`
   - `建议下一步`
8. 点击 `重试` 时，必须继续走用户当前选中的同一条链路，不允许偷偷切到另一条链路。
9. 当开关打开且 `AI` 没识别到有效文字时，应给出最小提示，不打开 `AI` 结果窗。

### 非功能需求

1. 默认行为不能影响当前老用户体验。
2. 不引入第三方依赖，继续优先使用原生与现有服务结构。
3. 不重做当前 `AI` 结果窗口结构。
4. 不重做长截图 `AI` 异步失效与单窗互斥机制。
5. 实现保持简单、可读、易维护。

## 方案比较

### 方案 A：直接替换旧链路

流程：

`截图 -> AI 视觉取字 -> AI 文本分析 -> AI 结果窗`

优点：

- 用户心智最统一
- 配置最少

缺点：

- 风险太高
- 无法保留当前稳定路径做对照
- 一旦视觉取字效果不稳定，会直接影响全部用户

### 方案 B：Settings 开关双链路切换

流程：

- 开关关闭：`截图 -> 本地 OCR -> AI 文本分析 -> AI 结果窗`
- 开关打开：`截图 -> AI 视觉取字 -> AI 文本分析 -> AI 结果窗`

优点：

- 风险最可控
- 默认不打扰现有用户
- 方便比较两条链路效果
- 与当前产品阶段最匹配

缺点：

- 需要同时维护两条输入链路
- `Settings` 会新增一项 AI 配置

### 方案 C：新链路失败后自动回退旧链路

优点：

- 理论上成功率更高

缺点：

- 用户不知道自己最后走的是哪条链路
- 调试和验证复杂
- 不利于判断视觉取字真实效果

### 推荐方案

选择方案 B。

原因：

- 它最符合“默认稳定、主动试用新能力”的产品节奏
- 可以让本轮范围集中在“增加可切换新链路”
- 不会把错误恢复、自动回退、链路猜测等复杂度提前带进来

## 设计方案

### 1. Settings 开关

在现有 `Settings` 页面中新增一个独立小节：

`AI 分析配置`

其中包含一个开关：

- 标题：`AI 使用视觉取字`
- 说明：`关闭时使用本地 OCR，开启时使用 AI 先识别截图文字再分析。`

建议放置位置：

- 位于 `HotKey 配置` 与 `保存目录配置` 之间

默认值：

- `false`

这样用户升级后不会自动切换到新链路，
必须主动打开才会走 `AI` 视觉取字。

### 2. AI 输入策略

本轮新增一个很小的 AI 输入策略概念，
只表达“AI 分析前的文字来自哪里”：

- `localOCR`
- `visionAI`

`Settings` 开关只负责映射到这个策略：

- `false` -> `localOCR`
- `true` -> `visionAI`

普通截图和长截图都会统一先解析当前策略，
再按策略拿文本，
最后汇聚到现有文本分析服务。

### 3. 服务拆分

#### `AIImageTextExtractionService`

新增一个服务，
专门负责：

`CGImage -> 视觉 AI -> 提取文本`

职责：

- 接收截图图片
- 将图片编码为可发送给视觉模型的输入
- 请求支持视觉的 AI 模型
- 返回提取出的纯文本

不负责：

- 报错解释
- 结果结构化
- 结果窗口展示

#### `AIAnalysisService`

继续保留现有职责：

`text -> AIAnalysisResult`

职责不变：

- 接收文本
- 调用 AI 文本分析
- 解析为：
  - `报错大意`
  - `可能原因`
  - `建议下一步`

本轮不把图片分析逻辑塞进这个服务里，
避免单个 service 同时承担“看图取字”和“文本分析”两种职责。

#### `CaptureSessionService`

继续作为流程编排层，
负责：

- 读取当前 AI 输入策略
- 普通截图 `AI` 链路编排
- 长截图 `AI` 链路编排
- 结果窗 loading / success / error 状态切换
- 长截图旧请求失效保护

### 4. 普通截图 AI 流程

当用户在普通截图编辑态点击 `AI`：

1. 读取当前开关状态
2. 弹出现有 `AI` loading 窗
3. 获取当前截图图像
4. 按策略取字：
   - `localOCR`：继续使用本地 `ocrService`
   - `visionAI`：使用 `AIImageTextExtractionService`
5. 若拿到有效文字，则交给 `AIAnalysisService`
6. 成功后展示现有 `AI` 结果窗
7. 失败则按对应错误类型处理

### 5. 长截图 AI 流程

长截图中的 `AI` 入口保持不变，
但中间取字路径同样切换为策略驱动：

- `localOCR`：
  `长图 -> 本地 OCR -> AI 文本分析`
- `visionAI`：
  `长图 -> AI 视觉取字 -> AI 文本分析`

长截图模式下必须继续保留已有机制：

- 根据长截图预览窗所在侧决定结果窗优先侧
- 同一时刻只保留一个结果窗
- 继续滚动、切到 `OCR`、保存、复制、取消时，旧 AI 请求失效
- 过期异步结果不能晚到覆盖当前状态

### 6. AI 视觉取字输出要求

视觉取字阶段只做一件事：

`尽量忠实提取截图中的文字`

要求：

- 不做解释
- 不做总结
- 不输出额外前言
- 不输出 Markdown 代码块
- 保持关键信息顺序
- 如果图片里没有足够可识别文字，则返回空或近空文本

这是为了让第二阶段文本分析继续接收稳定的文本输入，
并为后续多方向 AI 功能复用这一层能力。

## 错误处理

### 1. 开关关闭时，本地 OCR 无有效文字

只发生在 `localOCR` 链路。

表现：

- 保持当前老链路语义
- `toast`：`OCR 未识别到有效文本`
- 继续沿用现有 AI 错误展示逻辑

### 2. 开关打开时，AI 视觉取字请求失败

只发生在 `visionAI` 链路。

表现：

- `toast`：`AI 识别失败`
- 如果 loading 窗已显示，则切到 `AI` 错误窗
- 支持 `重试`

这里的失败包括：

- 图片编码失败
- 请求失败
- 响应解析失败
- 视觉模型接口异常

### 3. 开关打开时，AI 视觉取字成功但没有有效文字

只发生在 `visionAI` 链路。

表现：

- `toast`：`AI 未识别到有效文字`
- 不打开 `AI` 结果窗
- 如果此前已经显示 loading 窗，则直接关闭 loading 窗

这不是系统错误，
而是“识别不到文字内容”，
因此不进入 `AI` 错误结果窗。

### 4. AI 文本分析失败

两条链路都可能发生。

表现：

- `toast`：`AI 分析失败`
- 若结果窗已出现，则切到错误态
- 支持 `重试`

### 5. 重试规则

重试必须严格重走当前链路：

- `localOCR` 失败后点击重试，仍走 `localOCR`
- `visionAI` 失败后点击重试，仍走 `visionAI`

本轮不做自动回退，不允许在后台悄悄换链路。

## 数据与配置

新增配置项：

- key：`settings.aiUseVisionTextExtraction`
- default：`false`

本轮不新增：

- 第二套 AI Key
- 专门的视觉模型配置页面
- 更复杂的迁移逻辑

默认假设：

- 当前 AI 配置已可同时用于文本分析与视觉取字

如果后续发现视觉模型与文本模型必须分开配置，
再单独做下一轮设计。

## 验证方案

1. 开关默认关闭时，普通截图点击 `AI`，行为与当前版本一致。
2. 开关默认关闭时，长截图点击 `AI`，行为与当前版本一致。
3. 开关打开后，普通截图点击 `AI`，能够走视觉取字再分析，并展示现有结构结果。
4. 开关打开后，长截图点击 `AI`，能够走视觉取字再分析，并展示现有结构结果。
5. 开关关闭时，本地 OCR 无有效文字，仍然提示 `OCR 未识别到有效文本`。
6. 开关打开时，视觉取字失败，提示 `AI 识别失败`，并支持重试。
7. 开关打开时，视觉取字成功但没有有效文字，只提示 `AI 未识别到有效文字`，不打开结果窗。
8. 两条链路中任一条的文本分析失败时，提示 `AI 分析失败`，并支持重试。
9. 长截图模式下，继续滚动后旧 AI 异步结果仍不会晚到覆盖新状态。
10. `OCR`、复制、保存、`Pin`、热键设置、保存目录设置主链路不回归。

- `AI` 多方向菜单实现
- 摘要、翻译、待办提取等通用 AI 方向实现
- 表格转 CSV / Excel
- 图表趋势分析
- UI / HTML / CSS / Figma 识别
- 自动回退旧链路
- 根据不同链路展示不同风格的 `AI` 结果窗
- 视觉模型与文本模型分开配置

## 后续需求记录

### 1. AI 多方向菜单

目标交互：

`点击 AI -> 弹出方向列表 -> 选择分析方向 -> 打开 AI 结果窗`

候选方向包括：

- 摘要总结
- 翻译语言
- 待办提取
- 表格转 CSV
- 图表趋势分析
- UI / 代码识别

### 2. 两阶段文本复用

当本轮完成后，
后续多方向 AI 功能可以复用相同的“先取字，再处理”结构：

1. 第一步：按当前策略获取文本
2. 第二步：按不同方向切换 prompt 或结果结构

这也是本轮保持 `AIImageTextExtractionService` 与 `AIAnalysisService` 分层的主要原因之一。
