# Sprint 29 - AI 分析设计文档

## 目标

在现有截图编辑体验中，
增加一个面向开发报错场景的最小 `AI 分析` 流程。

第一版能力明确收敛为：

`开发报错截图 -> OCR 文本 -> AI 分析 -> 轻量结果面板`

本轮不尝试把产品扩展为通用 AI 助手。

---

## 背景

当前应用已经具备：

- 截图
- 编辑工具栏
- `OCR` 操作
- `OCR` 结果预览面板
- 保存 / 复制 / `Pin`
- 长截图

下一步真正有价值的提升，
不是继续增加截图编辑功能，
而是缩短下面这条链路：

`我看到了一个报错`

到：

`我知道下一步该怎么排查`

对于当前阶段，
最适合的做法是继续复用现有 `OCR` 能力，
只做面向开发报错的文本分析。

---

## 目标用户

核心用户：

- 单人开发者
- `Xcode` 编译报错截图用户
- `Terminal` 命令报错截图用户
- 日志或崩溃文本截图用户

本轮不面向以下场景：

- UI 逆向分析
- 图片理解
- 通用内容总结
- 设计稿转代码

---

## 需求

### 功能需求

1. 在现有编辑工具栏中新增 `AI` 按钮。
2. 用户点击 `AI` 后，应用先对原始截图区域执行 `OCR`。
3. 当 `OCR` 返回有效文本后，将文本发送给单一 AI 提供方分析。
4. 在当前截图流程中展示一个轻量结果面板。
5. 结果面板必须支持：
   - 复制
   - 重试
   - 关闭
6. 当本地配置缺失、`OCR` 无结果、请求失败或 AI 返回空结果时，必须给出明确反馈。

### 非功能需求

1. 仅支持手动触发。
2. 本轮不增加设置页里的 AI 配置项。
3. 本轮不支持截图图片直接上传给 AI。
4. 不影响现有保存 / 复制 / `OCR` / `Pin` / 长截图主链路。
5. 实现保持简单、清晰、可维护。

---

## 方案比较

### 方案 A：只做 `OCR` 文本的开发报错分析

流程：

`截图 -> AI 按钮 -> OCR -> 文本 AI 请求 -> 结果面板`

优点：

- 实现风险最低
- 请求成本较低
- 最适合开发报错截图场景
- 容易解释和验证

缺点：

- 无法覆盖纯视觉类截图
- 不适用于 UI 逆向分析

### 方案 B：`OCR` 优先，图片分析兜底

优点：

- 能力更完整
- 更接近未来扩展方向

缺点：

- 范围明显扩大
- 请求链路更复杂
- 错误处理更重
- 对当前验证目标不是必需

### 方案 C：只做图片分析

优点：

- 用户故事最直接

缺点：

- 对开发报错场景结果更不稳定
- 成本更高
- 浪费现有 `OCR` 能力积累

### 推荐方案

选择方案 A。

这是当前最小、最稳、最符合项目节奏的实现方式，
也能直接验证核心假设：

`开发者是否愿意留在截图编辑界面里完成第一次报错分析。`

## 设计方案

### 1. 入口

在现有编辑工具栏中新增一个：

`AI`

按钮。

它应放在现有 `OCR` 按钮附近，
因为两者都依赖原始截图区域，
而不是依赖编辑后的标注结果。

### 2. 输入来源

AI 分析固定基于原始截图区域，
不使用带标注的编辑结果。

这样可以保证行为与现有 `OCR` 保持一致，
避免箭头、文字、马赛克等编辑内容干扰分析输入。

### 3. AI 分析请求

应用将 `OCR` 文本发送给单一 AI 提供方。

本轮固定使用一套提示词，
重点面向：

- 编译错误
- Shell 错误
- 日志输出
- 崩溃相关文本

期望输出结构：

1. 报错大意
2. 可能原因
3. 建议下一步

为了降低第一版实现风险，
请求结构应采用最小形式：

- 顶层 `instructions`
- 顶层 `input`
- 显式设置 `store: false`

本轮不引入更复杂的多消息输入结构。

### 4. 结果展示

使用一个轻量浮动面板展示 AI 结果，
交互风格尽量复用现有 `OCR` 预览面板。

面板状态包括：

- 加载中
- 成功
- 失败

面板操作包括：

- 复制
- 重试
- 关闭

这样可以复用用户已经熟悉的 UI 心智模型，
避免为本轮引入全新的窗口体系。

### 5. 隐藏配置

本轮不增加设置页配置项。

AI 所需配置通过本地隐藏配置提供。

推荐方式：

- 用私有 `UserDefaults` 键保存 / 读取 API Key
- 用文档说明本地 `defaults write ...` 配置命令
- 配置命令必须使用应用真实 bundle id：`com.sheldon.TShot`

这是一个刻意的取舍：

- 可发现性较弱
- 实现范围更小

### 6. 错误处理

错误类型应明确区分：

- 未配置 API Key
- `OCR` 没识别出有效文本
- 网络请求失败
- AI 返回空结果

最低要求：

- 即时失败时展示 `toast`
- 当面板已出现时，把面板切换到错误状态

### 7. 交互约束

为了避免第一版出现状态混乱，
需要明确以下行为：

- AI 请求进行中时，工具栏 `AI` 按钮不可重复触发
- AI 请求进行中时，结果面板中的 `重试` 按钮禁用
- 点击 `关闭` 只关闭 AI 面板，不结束截图编辑态
- 点击 `关闭` 不取消已经发出的 AI 请求
- AI 分析始终基于原始截图区域执行 `OCR`，不读取标注结果

### 8. 默认模型选择

本轮默认模型建议使用：

`gpt-5.4-mini`

原因：

- 当前官方将其定位为更强的 mini 模型
- 更适合低延迟、小体量开发辅助场景
- 比使用不确定是否可用的旧模型名更稳妥

## 文件级拆分建议

最小且清晰的拆分方式如下：

- `CaptureOverlayView`
  负责新增 `AI` 工具栏按钮，并上抛用户意图。

- `CaptureOverlayService`
  负责继续转发新的 `AI` 事件。

- `CaptureSessionService`
  负责串联 `OCR`、AI 请求、结果面板状态与流程收尾。

- `AIAnalysisService`
  负责隐藏配置读取、请求构造、响应解析和 AI 错误定义。

- `AIAnalysisPreviewWindowService`
  负责加载 / 成功 / 失败三种展示状态。

- `AppSettings`
  负责新增隐藏配置键和默认模型常量。

- `TYScreenShotToolApp`
  负责把新服务接入应用启动时的依赖装配。

这样不需要大规模重构，
也符合当前项目以 `Service` 为主的组织方式。

---

## 验证方式

1. 进入截图编辑态后，确认工具栏出现 `AI` 按钮。
2. 使用包含清晰 `Xcode` 或 `Terminal` 报错的截图。
3. 点击 `AI` 后，确认界面进入加载状态。
4. 确认轻量结果面板中出现可读分析内容。
5. 确认点击 `复制` 可以复制分析结果。
6. 确认点击 `重试` 可以重新发起分析，而无需重新截图。
7. 确认点击 `关闭` 只关闭 AI 面板，不退出截图编辑态。
8. 确认 API Key 缺失、`OCR` 空结果和请求失败时都有明确反馈。
9. 确认保存 / 复制 / `OCR` / `Pin` / 长截图链路保持正常。

---

## 范围护栏

本轮明确不做：

- 图片上传分析
- AI 对话
- 提示词模板 UI
- 模型选择 UI
- AI 历史记录
- 自动修复报错
- 打开外部文档或链接

如果这些能力后续变得必要，
应进入新的 Sprint，而不是并入本轮。

---

## 结论

Sprint 29 应实现的是一个最小但真实有价值的 AI 工作流：

`开发报错截图 -> OCR -> AI 解释 -> 复制结果`

这是 TYScreenShotTool 从截图工具，
向截图触发工作流工具演进的最合理下一步。
