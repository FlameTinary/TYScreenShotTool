# Sprint 31 - 窗口悬停选择设计文档

## 目标

在现有截图触发体验中，
增加一个最小 `窗口悬停选择` 模式。

第一版能力明确收敛为：

`热键触发 -> 鼠标悬停命中整个应用窗口 -> 点击确认 -> 进入现有编辑态`

同时保持现有自由拖拽框选流程不变：

`热键触发 -> 按住并拖拽 -> 自由框选 -> 进入现有编辑态`

本轮不尝试实现窗口内部子区域识别，
也不重做当前截图编辑架构。

---

## 背景

当前应用已经具备：

- 全屏 Overlay
- 鼠标自由拖拽框选
- 框选后进入编辑态
- 复制 / 保存 / `OCR` / `AI` / `Pin` / 长截图

当前截图起手方式只有一种：

`按热键 -> 拖框 -> 松手 -> 进入编辑态`

对于“截整个应用窗口”这种高频场景，
用户仍然需要手动拖出一个尽量贴边的选区。

下一步更有价值的提升，
不是继续扩大编辑态能力边界，
而是让截图的第一步更省操作：

`我想截某个窗口`

到：

`我把鼠标移上去，点一下就选中了整个窗口`

对于当前阶段，
最适合的做法是只支持“整个应用窗口”的悬停命中，
并保留现有自由拖拽作为兜底与并行入口。

---

## 目标用户

核心用户：

- 单人开发者
- 高频截图某个应用窗口的用户
- 需要在“整窗截图”和“自由框选”之间快速切换的用户

本轮不面向以下场景：

- 窗口内部按钮或面板级识别
- 网页局部区域自动识别
- 复杂吸附规则
- 智能推荐截图区域

---

## 需求

### 功能需求

1. 热键触发截图后，Overlay 进入统一选择模式。
2. 当鼠标移动到可识别的应用窗口上方时，显示一个与窗口边界一致的高亮框。
3. 高亮框内部区域的遮罩应变为透明，视觉上与现有框选后的编辑区域一致。
4. 在悬停高亮阶段，应用仍未进入编辑态，只是候选窗口预览。
5. 用户移动鼠标到别的窗口时，候选高亮应随之切换。
6. 用户轻点鼠标左键时，确认当前候选窗口，并进入现有编辑态。
7. 如果用户按下鼠标后开始拖动，应立即切换到现有自由框选流程。
8. 当鼠标位于桌面空白区域或无法识别有效窗口时，不显示窗口高亮，回退为当前普通待命状态。

### 非功能需求

1. 本轮只支持“整个应用窗口”。
2. 不要求支持窗口内部子区域。
3. 不引入新的系统权限前提。
4. 不影响现有复制 / 保存 / `OCR` / `AI` / `Pin` / 长截图主链路。
5. 实现保持简单、清晰、可维护。

---

## 方案比较

### 方案 A：基于系统窗口列表实现整个窗口命中

流程：

`Overlay -> 鼠标移动 -> 命中当前指针下窗口 -> 显示候选高亮 -> 点击确认`

优点：

- 最符合本轮“整个窗口”目标
- 不改变现有编辑态主链路
- 能与当前自由拖拽框选并存
- 后续仍可继续扩展窗口过滤与子区域能力

缺点：

- 需要新增窗口命中与候选态逻辑
- 要处理桌面、无效窗口、特殊悬浮窗等边界

### 方案 B：基于辅助功能树识别窗口与区域

优点：

- 理论上更容易扩展到窗口内部子区域
- 未来能力上限更高

缺点：

- 范围明显扩大
- 可能引入新的权限与稳定性问题
- 对当前 `Sprint 31` 的 MVP 目标不是必需

### 方案 C：只做几何吸附或图像边缘猜测

优点：

- 早期实现看起来更轻

缺点：

- 不是对真实窗口的稳定识别
- 容易误判
- 用户心智不稳定
- 不适合作为截图工具的基础行为

### 推荐方案

选择方案 A。

这是当前最小、最稳、最符合项目节奏的实现方式，
也能直接验证核心假设：

`用户是否愿意在不拖框的情况下，用“悬停 + 点击”完成整窗截图。`

---

## 设计方案

### 1. 统一起手模式

热键触发后，
Overlay 仍进入当前的选择模式，
但该模式下同时允许两种起手路径：

- 鼠标移动：进入窗口候选判断
- 按住并拖拽：进入现有自由框选流程

这意味着本轮不新增独立的“窗口截图模式开关”，
而是在当前截图起手阶段直接增强交互。

### 2. 候选窗口预览

当鼠标未按下、仅在屏幕上移动时，
应用持续查找当前指针下方的可识别窗口。

若命中有效窗口：

- 显示一个与窗口矩形一致的高亮边框
- 候选区域内遮罩变为透明
- 视觉风格尽量复用当前选区边框与镂空效果

此时仍然不是编辑态，
只是“候选窗口预览态”。

若鼠标继续移动到其他窗口，
则候选矩形应随之更新。

### 3. 点击确认进入编辑态

当存在有效候选窗口时，
用户轻点鼠标左键，
应用应直接将该窗口矩形作为最终选区，
并进入现有编辑态。

进入编辑态后，
后续复制、保存、`OCR`、`AI`、`Pin`、长截图流程全部复用当前链路，
不新增专门的“窗口来源编辑态”分支。

### 4. 按下拖拽切回自由框选

如果用户按下鼠标左键后发生拖动，
则立即放弃当前候选窗口，
切回现有自由框选逻辑。

本轮明确采用以下规则：

- 鼠标按下本身不进入编辑态
- 只有“点击后松开且未拖动”才算确认候选窗口
- 一旦发生拖动，就完全按现有自由框选行为处理

这样可以保持用户已有肌肉记忆，
同时避免窗口吸附与自由框选互相干扰。

### 5. 空白区域与无效窗口回退

如果鼠标当前位于以下位置：

- 桌面空白区域
- 壁纸区域
- 无法获得稳定窗口边界的位置

则不显示候选窗口高亮。

Overlay 应回到当前普通待命外观，
允许用户像现在一样直接开始拖拽自由框选。

这是一条明确的兜底规则：

`窗口命中失败时，不报错，不阻断，只回退到现有自由框选。`

### 6. 范围控制

为了避免第一版复杂度失控，
需要明确以下不做项：

- 不支持窗口内部子区域
- 不支持自动识别控件、面板、代码编辑区
- 不支持复杂吸附优先级设置
- 不支持额外设置页选项
- 不支持多种窗口选择模式切换 UI

后续如果需要扩展到子区域识别，
应作为独立 Sprint 继续设计。

### 7. 状态与职责边界

本轮优先保持 `CaptureSessionService` 主状态机最小化，
不为了窗口候选预览引入新的复杂会话状态。

建议职责边界如下：

- `CaptureOverlayView`
  负责鼠标移动、候选窗口预览、点击确认与拖拽分叉
- `CaptureOverlayService`
  负责 Overlay 视图和屏幕坐标转换，以及窗口矩形查询的转发
- `CaptureSessionService`
  继续只接收“最终确认的选区矩形”，并复用现有编辑态入口

也就是说，
候选窗口预览属于 Overlay 内部交互，
而不是新的全局 Capture 会话阶段。

### 8. 错误处理与稳定性原则

本轮不把“命中不到窗口”视为错误。

最低要求：

- 获取不到窗口时静默回退到普通待命态
- 点击空白区域时不应错误进入编辑态
- 特殊窗口无法稳定命中时，不破坏当前自由框选主链路

实现上应优先保证：

`自由框选永远可用`

而不是追求所有窗口类型都必须被识别。

---

## 验证方式

### 场景 1

热键触发截图后，
鼠标移动到普通应用窗口上方时，
可看到与窗口边界一致的高亮候选框。

### 场景 2

鼠标继续移动到另一个窗口时，
候选高亮会跟随切换到新的窗口。

### 场景 3

当鼠标位于桌面空白区域时，
不显示候选窗口高亮，
Overlay 保持普通待命状态。

### 场景 4

当存在候选窗口时，
用户轻点鼠标左键，
应用直接以该窗口矩形进入现有编辑态。

### 场景 5

当用户按下鼠标后开始拖拽时，
应用会放弃候选窗口，
并按现有自由框选流程运行。

### 场景 6

通过窗口悬停确认进入编辑态后，
复制、保存、`OCR`、`AI`、`Pin`、长截图主链路保持正常。

---

## 结果预期

如果本轮完成顺利，
应用将新增一条更轻量的截图起手路径：

`热键 -> 悬停窗口 -> 点击 -> 编辑态`

同时保留原有路径：

`热键 -> 拖拽框选 -> 编辑态`

这会让“整窗截图”明显更快，
又不会牺牲当前自由框选的灵活性，
符合项目现阶段 `MVP / KISS / YAGNI` 的推进节奏。
